# 校园鲜达模块一需求文档索引

## 1. 文档用途

本目录记录“校园鲜达”课程大作业模块一的业务需求，供三名成员后续独立完成测试设计、测试实现、缺陷登记和质量改进。

- 项目基线：`demo-v0.3`（提交 `84aa763`）
- 需求负责人：成员 A（组长）
- 适用范围：商品浏览、购物车和订单主流程
- 需求来源：现有“校园鲜达”代码、课程作业要求及小组分工

这些文档描述系统应具备的行为。表格中的“当前状态”用于区分现有能力和后续改进项，不表示相关功能已经通过测试。

| 成员 | 负责范围 | 需求文档 | 需求编号前缀 |

| 成员 C | 购物车、订单、库存、集成执行和演示 | [成员 C：购物车与订单模块需求](member-c-cart-order-requirements.md) | `C-CART`、`C-ORD`、`C-INV`、`C-INT` |

## 3. 当前状态定义

| 状态 | 含义 |
| --- | --- |
| 已实现 | 当前基线已经具备主要业务行为，仍需由负责人自行验证 |
| 部分实现 | 主流程存在，但校验、权限、异常处理或数据一致性仍不完整 |
| 待实现 | 当前基线缺少该能力，需要负责人完成代码改进 |

## 4. 共同规则

1. 每项需求使用固定编号，代码提交、缺陷记录、测试记录和报告应引用对应编号。
2. 商品金额使用十进制数计算和保存；库存、购买数量、浏览次数不得为负数。
3. 登录用户只能读取或修改属于自己的地址、购物车、订单和浏览历史。
4. 逻辑删除或失效的商品不得继续进入新的购物流程。
5. 页面异常应转换为明确、可理解的提示，不能向普通用户展示调试堆栈。
6. 演示数据不得包含往届项目中的真实账号、地址或其他个人信息。

## 5. 课程作业边界

本目录只提供需求依据，不包含模块一测试用例、测试数据组合、自动化测试脚本或测试结论。成员 B、成员 C 应根据课程要求独立完成自己负责模块的测试设计和执行，并使用各自 GitHub 账号提交代码与文档，以形成可核验的个人贡献记录。

组长汇总时应检查需求编号、提交记录、缺陷编号、修复提交和报告内容之间能否相互追踪。
